# GameMall 高并发订单链路压测研究报告

## 摘要

本报告围绕数字游戏商城系统 GameMall 的核心交易链路开展压力测试研究，重点评估系统在并发下单、库存扣减、订单幂等和状态流转场景中的正确性与稳定性。实验采用自动化并发单元测试与真实 HTTP 接口压测相结合的方法，对订单创建接口进行并发请求模拟。结果显示，在库存为 120、并发用户数为 200、并发度为 64 的场景下，系统成功创建 120 笔订单，拒绝 80 次超库存请求，数据库订单明细总量与库存扣减量完全一致，未发生超卖。在同一用户同一幂等键 30 并发请求场景下，系统仅创建 1 笔订单并仅扣减 1 件库存，验证了幂等控制的有效性。

关键词：游戏商城；高并发；压力测试；库存扣减；幂等控制；Spring Boot；MySQL

## 1. 研究背景

数字游戏商城在促销、上新、限量发售等业务场景下，经常面临短时间内大量用户同时浏览商品、加入购物车和提交订单的访问压力。其中，订单创建链路是系统正确性要求最高的部分之一：系统既要允许大量请求并发进入，又不能出现库存超卖、重复下单、订单状态错乱或库存重复回滚等问题。

GameMall 项目模拟类 Steam 游戏商品交易平台，包含游戏展示、分类检索、购物车、订单创建、支付模拟、库存管理和后台商品运营等模块。本研究聚焦订单创建链路，评估其在高并发条件下的业务一致性。

## 2. 研究问题

本研究回答以下问题：

- RQ1：在并发下单场景中，系统是否能够避免库存超卖？
- RQ2：在用户重复提交订单时，系统是否能够保证幂等性？
- RQ3：在中小型项目部署配置下，订单接口是否具备可接受的并发处理能力？
- RQ4：当前系统仍存在哪些性能瓶颈和工程改进空间？

## 3. 系统设计与并发控制机制

### 3.1 核心交易流程

订单创建流程设计如下：

1. 接收用户订单请求，校验 JWT 身份。
2. 读取请求中的 `idempotencyKey`，用于防重复提交。
3. 创建 `CREATING` 状态订单骨架。
4. 在同一事务内执行库存扣减。
5. 写入订单明细。
6. 将订单状态推进为 `PENDING_PAYMENT`。
7. 返回订单详情。

### 3.2 防超卖策略

库存扣减不依赖 JVM 内存锁，而是交给 MySQL 执行原子条件更新：

```sql
update games
set stock = stock - #{quantity}, updated_at = now()
where id = #{id}
  and status = 1
  and stock >= #{quantity}
```

该语句具备两个关键特征：

- 单条 SQL 在 InnoDB 中具备原子性。
- `stock >= quantity` 将库存校验与扣减合并，避免先查后改造成的竞态窗口。

### 3.3 幂等控制策略

订单表增加字段 `idempotency_key`，并建立唯一索引：

```sql
unique key uk_orders_user_idempotency (user_id, idempotency_key)
```

同一用户使用同一幂等键重复提交时，只会创建一笔订单。若并发请求读取到 `CREATING` 中间态，服务会短暂等待订单完成后返回最终订单，避免返回半成品数据。

### 3.4 状态流转控制

订单状态模型如下：

| 状态码 | 状态 | 含义 |
|---:|---|---|
| 5 | CREATING | 订单创建中 |
| 10 | PENDING_PAYMENT | 待支付 |
| 20 | PAID | 已支付 |
| 30 | CANCELLED | 已取消 |
| 40 | CLOSED | 已关闭 |

支付和取消均使用状态条件更新，只允许待支付订单继续流转，从而降低重复支付、重复取消和库存重复回滚风险。

## 5. 实验方法

### 5.1 自动化并发测试

自动化测试使用 JUnit 构造并发场景，重点验证业务正确性。测试命令：

```powershell
mvn -q test
```

测试场景包括：

- 200 个线程同时下单，初始库存为 40。
- 30 个线程使用同一用户、同一 `idempotencyKey` 同时下单。

### 5.2 HTTP 接口压力测试

HTTP 压测脚本使用 Windows PowerShell RunspacePool 实现并发请求，模拟多个用户注册、登录并调用订单接口。

命令如下：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/stress-order.ps1 -Users 200 -Concurrency 64 -GameId 1 -Quantity 1
```

其中：

- `Users=200` 表示总请求用户数为 200。
- `Concurrency=64` 表示最大并发度为 64。
- `GameId=1` 表示压测目标商品。
- `Quantity=1` 表示每个用户购买 1 件。

### 5.3 数据库一致性校验

压测完成后，通过 SQL 校验以下指标：

- 商品剩余库存。
- 成功订单数量。
- 订单明细数量。
- 订单明细购买总量。

## 6. 实验结果

### 6.1 自动化并发测试结果

| 场景 | 并发规模 | 初始库存 | 成功数 | 拒绝数 | 最终库存 | 结论 |
|---|---:|---:|---:|---:|---:|---|
| 并发下单防超卖 | 200 线程 | 40 | 40 | 160 | 0 | 未超卖 |
| 同幂等键重复提交 | 30 线程 | 10 | 1 笔订单 | 29 次复用结果 | 9 | 幂等有效 |

### 6.2 HTTP 订单压测结果

压测输出：

```text
users          : 200
concurrency    : 64
success        : 120
failed         : 80
elapsedSeconds : 5.97
throughput     : 33.48
```

数据库校验结果：

```text
game_id=1 stock=0
status=10 count=120
order_items=120
total_quantity=120
```

解释：

- 商品 1 初始库存为 120。
- 200 次并发下单中，系统成功接受 120 次请求。
- 其余 80 次请求因库存不足被拒绝。
- 订单明细数量为 120，订单明细购买总量为 120。
- 最终库存为 0。

由此可见，成功订单数量、明细购买总量和库存扣减量三者一致，未出现超卖。

### 6.3 HTTP 幂等压测结果

测试场景：同一用户、同一 `idempotencyKey`、30 个并发请求同时创建游戏 2 订单。

接口返回聚合结果：

```text
30 True, 201, 10, 1, success
```

数据库校验结果：

```text
game_id=2 stock=79
idempotent_orders=1
idempotent_items=1
```

解释：

- 30 次请求全部成功返回。
- 所有请求返回同一订单 ID。
- 数据库只创建 1 笔订单。
- 数据库只创建 1 条订单明细。
- 商品库存只扣减 1 件。

因此，订单幂等机制在并发重复提交场景下有效。

## 7. 分析与讨论

### 7.1 正确性分析

本实验中最重要的评价指标不是单纯吞吐量，而是交易链路的一致性。结果表明，GameMall 在并发下单时能够保持以下不变量：

```text
初始库存 = 成功订单购买总量 + 最终库存
```

在 HTTP 压测中：

```text
120 = 120 + 0
```

该等式成立，说明库存扣减与订单明细写入结果一致。

### 7.2 幂等性分析

重复提交是订单系统常见问题，可能由前端重复点击、网络重试、网关重放或客户端超时重试导致。本系统通过数据库唯一约束保证最终一致性，即使多个请求同时进入，也只有一个请求能成功创建订单记录，其余请求会复用已创建订单。

这种方案比单纯使用 JVM 锁更适合多实例部署，因为唯一索引由数据库统一裁决，不依赖单个应用进程。

### 7.3 性能分析

在本地开发机环境下，200 用户、64 并发订单压测达到约 33.48 req/s。该值包含用户注册、登录和订单创建全流程开销，因此不等同于纯订单接口吞吐量。对于课程项目或中小型公司内部演示环境，该结果可以体现系统具备基础并发处理能力。

若只测试已登录用户的纯下单接口，理论吞吐量会高于本次结果，因为注册、登录、JWT 生成和密码校验会占用额外时间。

## 8. 有效性威胁

本实验仍存在以下限制：

- 测试环境为单机本地环境，无法完全代表生产服务器性能。
- HTTP 压测工具基于 PowerShell RunspacePool，不如 JMeter、wrk、k6 等专业压测工具稳定。
- 当前压测关注订单创建链路，没有覆盖商品列表缓存、购物车、支付回调和后台运营接口。
- 当前报告未采集 CPU、内存、GC、MySQL 慢查询、连接池等待时间等系统级指标。
- Redis 在商品缓存链路中使用，但订单扣减核心链路主要依赖 MySQL，尚未引入 Redis 预扣库存或消息队列削峰。

## 9. 工程改进建议

后续可从以下方向继续增强：

- 使用 JMeter、k6 或 wrk 对接口进行阶梯压测、稳定性压测和峰值压测。
- 引入 Micrometer + Prometheus + Grafana 采集 QPS、P95、P99、错误率、连接池等待时间和 JVM 指标。
- 对订单创建接口单独压测，排除注册和登录开销。
- 使用 Redis Lua 脚本进行热点库存预扣，再通过异步队列落库，提升秒杀类场景吞吐。
- 引入 MQ 进行订单削峰，降低瞬时流量对 MySQL 的写入压力。
- 对订单超时取消任务增加分片扫描或基于延迟队列处理，避免大量超时订单集中扫描。
- 使用 Testcontainers 或独立压测数据库，保证实验环境可重复。

## 10. 结论

本研究通过自动化并发测试与真实 HTTP 压测验证了 GameMall 核心订单链路的并发正确性。实验结果表明，系统能够在多用户并发下单场景中避免库存超卖，并能在重复提交场景中保证订单幂等。虽然当前吞吐量测试受限于本地环境和脚本工具，但从业务一致性角度看，系统已经具备中小型项目工程落地所需的基础并发控制能力。
